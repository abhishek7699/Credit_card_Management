# Data Model: Fraud Detection Service

**Date**: 2026-06-12
**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

All tables reside in the `fraud-detection-service`'s own CockroachDB schema. No other
service may query these tables directly (Constitution Principle V).

---

## Entity: FraudAlert

Persisted when one or more fraud rules trigger on a transaction. One record per unique
transaction (a transaction that triggers multiple rules produces one alert listing all
rule names).

**Java class**: `com.creditcard.frauddetection.domain.FraudAlert`

**Table**: `fraud_alerts`

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | UUID | PK, `DEFAULT gen_random_uuid()` | Unique alert identifier |
| `transaction_id` | UUID | NOT NULL | Identifier from the inbound event |
| `card_token` | VARCHAR(512) | NOT NULL | Opaque vault token; never a raw PAN |
| `amount` | DECIMAL(15,4) | NOT NULL | Transaction amount |
| `currency_code` | CHAR(3) | NOT NULL | ISO 4217 currency code |
| `triggered_rules` | TEXT | NOT NULL | Comma-delimited rule names (e.g., `VELOCITY_EXCEEDED,BLACKLISTED_CARD`) |
| `detected_at` | TIMESTAMPTZ | NOT NULL, `DEFAULT now()` | Timestamp of detection |

**Indexes**: `idx_fraud_alerts_tx_id (transaction_id)`, `idx_fraud_alerts_card (card_token)`

**Java mapping notes**:
- `triggeredRules` is mapped as `List<String>` using a JPA `AttributeConverter` that
  converts between `List<String>` and comma-delimited TEXT.
- `id` is generated by the database; `@GeneratedValue` not used — set by DB default.

## Entity: FraudRuleConfig

Configurable parameters for each fraud rule. One row per rule type. Updated by risk
managers without requiring a service restart (SC-004).

**Java class**: `com.creditcard.frauddetection.domain.FraudRuleConfig`

**Table**: `fraud_rule_configs`

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `rule_type` | VARCHAR(50) | PK | One of: `VELOCITY_EXCEEDED`, `AMOUNT_ANOMALY`, `BLACKLISTED_CARD` |
| `enabled` | BOOLEAN | NOT NULL, `DEFAULT true` | Whether this rule is active |
| `parameters` | TEXT | NOT NULL, `DEFAULT '{}'` | JSON string with rule-specific thresholds |
| `updated_at` | TIMESTAMPTZ | NOT NULL, `DEFAULT now()` | Last configuration update timestamp |

**Seed data (V2 migration)**:

| rule_type | enabled | parameters |
|-----------|---------|------------|
| `VELOCITY_EXCEEDED` | true | `{"maxTransactions": 5, "windowMinutes": 10}` |
| `AMOUNT_ANOMALY` | true | `{"multiplier": 3.0, "lookbackDays": 30, "absoluteCeiling": 10000.00}` |
| `BLACKLISTED_CARD` | true | `{}` |

**Parameter schemas**:

- `VELOCITY_EXCEEDED`: `{ "maxTransactions": int, "windowMinutes": int }`
  - `maxTransactions`: maximum number of allowed transactions in the time window before the rule fires
  - `windowMinutes`: length of the rolling time window in minutes
- `AMOUNT_ANOMALY`: `{ "multiplier": double, "lookbackDays": int, "absoluteCeiling": double }`
  - `multiplier`: factor applied to average spend; amount > multiplier × average → triggers
  - `lookbackDays`: how many days of history to use for average calculation
  - `absoluteCeiling`: baseline amount used when a card has no transaction history
- `BLACKLISTED_CARD`: no parameters; the blacklist content is in `blacklist_entries`

## Entity: BlacklistEntry

Records card tokens explicitly prohibited from transacting. Managed by risk operations.

**Java class**: `com.creditcard.frauddetection.domain.BlacklistEntry`

**Table**: `blacklist_entries`

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `card_token` | VARCHAR(512) | PK | Opaque vault token of the blocked card |
| `reason` | VARCHAR(255) | nullable | Human-readable reason for blacklisting |
| `added_at` | TIMESTAMPTZ | NOT NULL, `DEFAULT now()` | Date/time the card was added to the blacklist |

**Relationships**: None. Flat lookup table.

## Entity: TransactionRecord

Lightweight history of every successfully processed transaction. Used by velocity and
amount anomaly rules to derive per-card statistics. Written for every event (clean or
fraudulent) as part of the same atomic transaction that persists idempotency and alert data.

**Java class**: `com.creditcard.frauddetection.domain.TransactionRecord`

**Table**: `transaction_records`

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | UUID | PK, `DEFAULT gen_random_uuid()` | Surrogate key |
| `transaction_id` | UUID | NOT NULL, UNIQUE | Original transaction identifier (prevents duplicate records) |
| `card_token` | VARCHAR(512) | NOT NULL | Opaque vault token |
| `amount` | DECIMAL(15,4) | NOT NULL | Transaction amount |
| `currency_code` | CHAR(3) | NOT NULL | ISO 4217 currency code |
| `occurred_at` | TIMESTAMPTZ | NOT NULL | Timestamp from the original event (`TransactionInitiatedEvent.occurredAt`) |

**Indexes**: `idx_tx_records_card_time (card_token, occurred_at)` — covers both the velocity
count query (`WHERE card_token = ? AND occurred_at > ?`) and the anomaly average query.

**Query patterns**:
- Velocity check: `COUNT(*) WHERE card_token = ? AND occurred_at > NOW() - INTERVAL 'N minutes'`
- Anomaly baseline: `AVG(amount) WHERE card_token = ? AND occurred_at > NOW() - INTERVAL 'N days'`

## Entity: ProcessedEvent

Idempotency guard. One record per successfully processed event. Combined with
`ON CONFLICT DO NOTHING` to guarantee exactly-once processing (Constitution Principle III).

**Java class**: `com.creditcard.frauddetection.domain.ProcessedEvent`

**Table**: `processed_events`

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `event_key` | VARCHAR(255) | PK | Idempotency key: `fraud:{eventType}:{eventId}` |
| `processed_at` | TIMESTAMPTZ | NOT NULL, `DEFAULT now()` | When first processed |

---

## Entity Relationships

```text
TransactionInitiatedEvent (inbound Kafka)
         │
         ├─► ProcessedEvent       (1 per event — idempotency guard)
         ├─► TransactionRecord    (1 per event — history for rule calculations)
         └─► FraudAlert           (0 or 1 per event — only when rules trigger)

FraudRuleConfig                   (configuration for each rule type — read at evaluation)
BlacklistEntry                    (flat lookup — read by BlacklistRule)
```

---

## State Transitions

`FraudAlert` is insert-only (no updates or deletes). `TransactionRecord` is insert-only.
`BlacklistEntry` supports inserts and deletes (card tokens added/removed by risk managers).
`FraudRuleConfig.enabled` and `FraudRuleConfig.parameters` are updated in place by risk
managers to change thresholds without redeployment.
